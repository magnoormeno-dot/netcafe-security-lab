# Feedback Request Template

Use this text when asking a real operator, IT contractor, SOC analyst, or
security practitioner to review the CafeSec Lab pilot workflow. Do not imply that
they endorse the project. Ask only for practical feedback they are comfortable
posting publicly.

## Short Message

```text
Hi,

I am building CafeSec Lab, a defensive security research project for shared-PC venues such as internet cafes, gaming venues, esports hotels, kiosks, and managed PC fleets.

I am looking for practical feedback on whether the current synthetic pilot workflow would make sense to a real operator or IT contractor.

Project home:
https://cafeseclab.com/

Feedback issue:
https://github.com/magnoormeno-dot/netcafe-security-lab/issues/3

Useful feedback would be things like:
- which intake fields are unrealistic or too sensitive;
- which alerts would create too much operational fatigue;
- what a non-specialist venue owner would need in the executive summary;
- what should stay out of scope for a first pilot.

Please do not post customer data, credentials, vendor names, screenshots from production systems, private network diagrams, or bypass details. High-level operational feedback is enough.

Thanks.
```

## What Counts As Useful Public Feedback

Good feedback can be short. Examples:

- "This intake field is too sensitive for an operator to post publicly."
- "A weekly review cadence is more realistic than daily review for a small
  venue."
- "The executive summary should include cost, expected downtime, and who needs
  to approve re-baselining."
- "Service restart alerts are common during launcher updates; the workflow
  should distinguish expected updater restarts from unexplained restarts."

Do not ask anyone to share private incidents, live logs, credentials, customer
records, or vendor-specific weaknesses in public.
