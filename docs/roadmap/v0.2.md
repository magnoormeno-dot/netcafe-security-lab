# CafeSec Lab v0.2 Roadmap

This roadmap defines the next public milestone after `v0.1.1`. It is intentionally
operational: the project should improve the ability of a real venue operator,
SOC analyst, or software vendor to apply the guidance without expanding into
offensive tooling or unverifiable claims.

It implements the current [project goal](project-goal.md): a repeatable
defensive workflow for shared-PC venues.

## Milestone Goal

`v0.2.0` should turn the initial research preview into a small, repeatable
defensive workflow:

- choose a shared-PC venue profile;
- apply the relevant checklist sections;
- deploy the integrity monitor with a documented baseline process;
- tune detection rules with recorded false-positive decisions;
- produce an operator-readable summary of residual risks and next controls.

## Workstream 1: Operator Pilot Workflow

Deliverables:

- a short operator executive summary template
  ([available](../operators/executive-summary-template.md));
- a one-page pilot intake checklist for venue size, billing architecture,
  Windows version, network segmentation, restoration system, and logging state;
- a post-pilot summary template that separates observed facts, assumptions,
  recommended controls, and deferred work;
- a clear statement that public examples are anonymized and not field-validation
  claims unless evidence is available.

Progress:

- synthetic shared-PC venue pilot package:
  [`docs/pilot/synthetic-shared-pc-venue/`](../pilot/synthetic-shared-pc-venue/)
- operator executive summary template:
  [`docs/operators/executive-summary-template.md`](../operators/executive-summary-template.md)

Acceptance criteria:

- templates can be completed without exposing vendor names, customer identities,
  credentials, or network diagrams;
- recommendations map back to existing checklist sections;
- every risk statement includes at least one verification or mitigation step.

## Workstream 2: Integrity Monitor Packaging

Deliverables:

- a documented Windows scheduled-task deployment example;
- a minimal sample baseline lifecycle: create, verify, scan, review, rotate;
- clearer operator guidance for where baseline files and alert logs should live;
- a release artifact checklist for Python packaging and configuration examples.

Acceptance criteria:

- CI remains green on Ubuntu and Windows;
- `ruff`, `mypy`, and `pytest` pass before tagging;
- README commands are copy-paste testable in a clean virtual environment;
- deployment guidance does not assume administrator access beyond what is stated.

## Workstream 3: Detection Rule Tuning Evidence

Deliverables:

- one synthetic event fixture per Sigma rule;
- one documented benign scenario per rule that explains likely false positives;
- a filled example tuning register based on synthetic data;
- a short explanation of when a rule should be disabled, narrowed, or escalated.

Acceptance criteria:

- Sigma and YARA content stays vendor-neutral;
- rules do not include bypass instructions or tool-specific abuse walkthroughs;
- false-positive documentation remains honest about operational fatigue;
- ATT&CK mappings are reviewed against the technique descriptions.

## Workstream 4: Research Notes

Deliverables:

- one case-study style post using a fully anonymized scenario;
- one Q&A style post answering practical operator questions;
- one detection deep-dive explaining the design of a single rule family.

Acceptance criteria:

- posts use different structures rather than repeating the same essay format;
- no post names a vendor or venue unless coordinated disclosure requirements are
  satisfied;
- threat discussion is paired with detection, mitigation, or validation guidance;
- outbound links point to `https://cafeseclab.com/` or
  `https://research.cafeseclab.com/` as appropriate.

## Release Criteria

Tag `v0.2.0` only when all of the following are true:

- the project health sweep in `docs/maintenance/project-health.md` passes;
- root site, research site, and `security.txt` are reachable over HTTPS;
- CI is green after the final release commit;
- release notes list defensive value, known limitations, and non-goals;
- no public file contains personal Gmail addresses, old author names, stale
  GitHub Pages URLs, or region-specific positioning that conflicts with the
  current public scope;
- at least one user-facing workflow has improved beyond documentation polish.

## Deferred Beyond v0.2

These items are useful but should not block `v0.2.0`:

- Wazuh or OSSEC integration examples;
- signed Windows installer packaging;
- Docker or Ansible deployment for a small SOC stack;
- vendor-facing SDK or hardening library;
- formal academic paper outline.
